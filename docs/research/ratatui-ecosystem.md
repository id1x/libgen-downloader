# Research: ratatui component kits and patterns for the BROWSE spec's UI needs

**Resolves:** id1x/libgen-downloader#24 ("Which ratatui component kits and patterns cover the BROWSE spec's UI needs?") · parent map #13 · feeds #21 (workspace structure)
**Date:** 2026-11-15 · **Branch:** `research/ratatui-ecosystem` (throwaway, never merged — no PR)
**Method:** every version / MSRV / dependency claim below was pulled from the crates.io API, docs.rs, or the crate's own source on 2026-11-15. App surveys were read from each repo's default branch the same day (GitHub raw + code search). The rendering requirements come from the BROWSE spec (`docs/libgen-downloader master detail TUI redesign — implementation spec.md` §3–§4); the hand-roll inventory comes from the #15 spike at `2f28790` (`spike/ratatui-browse/`). Nothing here was compiled or run — compat claims rest on published dependency specs, flagged where that matters.
**Doc location note:** lives in `docs/research/` next to the other research tickets' docs.

## Verdict

There is **no ratatui "component kit" that covers the BROWSE screen as a kit** — the ecosystem's real shape is (a) ratatui's own builtin widgets, (b) a ratatui-org suite of small single-purpose widget crates (`tui-widgets`), and (c) a handful of tiny maintained crates for width-correct text math. The spike hand-rolled more than it had to: **four of its seven helpers are already builtin in ratatui 0.30** (list scroll windows with scroll-off, progress bars, popup clearing, word wrap), and the two real gaps — `…` ellipsis truncation and text editing — are covered by small, actively maintained crates the prominent apps themselves use.

Recommendation in one line each:

- **Adopt:** `unicode-ellipsis` (the `…` truncation), `unicode-truncate` (exact-width padding/truncation), `tui-input` (search line), `throbber-widgets-tui` (spinners), `tui-scrollview` (Queue-panel scroll, the one place a plain list widget doesn't fit).
- **Use builtins the spike missed:** `Table`/`List` with `scroll_padding(2)` (kills the hand-rolled scroll window), `Gauge`/`LineGauge` (kills the `bar()` string builder), `Paragraph` + `Wrap` (full-detail word wrap), `Clear` + `Block` titles (overlays, tab titles).
- **Hand-roll (thin glue, as every surveyed app does):** the key-hint footer line builder (~30 lines; no crate exists), the centered-dimmed-overlay composition (~15 lines; `tui-popup` doesn't dim and the spec pins exact box geometry), and the focus-mode key router (spec §4 mandates a single central router — a framework would fight it).

Consistent with #17's crates-first rule: everything adopted is maintained, pure Rust (no C deps, no musl assumptions — cargo-zigbuild linux-gnu targets unaffected), and MSRV ≤ 1.88, well under the project's 1.92 floor set by ort.

## What the spike hand-rolled (inventory)

`spike/ratatui-browse/src/ui/mod.rs` @ `2f28790`: `trunc()` (char-count truncation with `…`), `pad_right`/`pad_left` (manual pad strings), `bar()` (█/░ builder), `center_rect`, `dim_except` (buffer post-process adding `Modifier::DIM` outside a keep-rect), `key_hint`/`hints_line` (footer spans with `…`); `ui/results.rs`: `adjust_window()` scroll-off-2 window and a braille spinner frame array; `layout_metrics.rs`: breakpoints and column math.

Two of these are not merely reinvented wheels — they are **subtly wrong** relative to the spec's own examples: `trunc`/`pad_*` count `char`s, not display columns, so any libgen result with CJK/wide characters (real titles do exist) would misalign the §3 column table and break the `…` budget. This is exactly what the `unicode-*` crates exist for and the strongest argument for adopting them rather than "fixing" the helpers.

## ratatui 0.30 builtins the spike didn't use

Base versions (cross-checked against the #17 doc): `ratatui` 0.30.2 (released 2026-06-19, MSRV 1.88, split into `ratatui-core` 0.1.2 / `ratatui-widgets` 0.3.2 / `ratatui-crossterm` 0.1.2; crossterm 0.29.0). Changelog: [ratatui/ratatui CHANGELOG.md](https://github.com/ratatui/ratatui/blob/main/CHANGELOG.md).

1. **`Table`** (`ratatui-widgets/src/table.rs`): `header()`, `widths()` as `Constraint`s, `highlight_style`, `highlight_symbol`, and **`scroll_padding`** — "sets the number of rows to keep visible before and after the [selected row]" ([source](https://github.com/ratatui/ratatui/blob/main/ratatui-widgets/src/table.rs), `scroll_padding` at line 746). The §3 column table (cursor 3 / # 3 / ext 5 / title flex / author 16-or-14 / size 6 right / st 4 right) maps nearly 1:1; per-column alignment is done via `Line::alignment` inside each `Cell`.
2. **`List` + `scroll_padding`** (same story, `ratatui-widgets/src/list.rs:400-416`; shipped in **0.26.2**, per [CHANGELOG](https://github.com/ratatui/ratatui/blob/main/CHANGELOG.md) `Fixes: #955`). The stateful render calls `get_items_bounds(selected, offset, height)` and rewrites `state.offset` so the selection stays visible (`list/rendering.rs:60-63`) — the spike's `adjust_window()` reimplements this, minus scroll-off. `scroll_padding(2)` reproduces §6.2's "keep the cursor at least 2 rows from the edges" exactly.
3. **`Gauge`** (`gauge.rs:148` `use_unicode`) and **`LineGauge`**: ratio-based bars with partial-cell precision via unicode block chars — replaces `bar()` and renders §3's `↓ <bar> NN%` and §5.3's summary bar.
4. **`Paragraph` + `Wrap`** (with `reflow` word-wrapping, `ratatui-widgets/src/reflow.rs`): covers §5.7's "long values wrapped (not truncated)" without `textwrap`.
5. **`Clear`** widget: the documented erase-behind primitive for overlays (the spike uses it).
6. **`Block` titles**: multi-span, per-span-styled titles with `title_top(...)`/`right_aligned()` — covers `Detail │ Queue N` with bold/dim spans and the right-aligned `v` hint (the #15 verdict's "manual width math + title_top(right_aligned)" point).
7. **`Scrollbar`** widget (`scrollbar.rs`): available if the queue panel ever wants one; the spec doesn't ask.
8. **`Flex`** layout (0.26+) exists but does **not** express "55 % of width, minimum 56 columns" as a single constraint — keep that arithmetic in the spec-mandated pure `compute_layout()`.

**The ellipsis gap is real:** ratatui clips `Line`s to the render area automatically and alignment-aware (PRs [#987](https://github.com/ratatui/ratatui/pull/987), [#1432](https://github.com/ratatui/ratatui/pull/1432), title-truncation fixes #1931/#1973 — all in the [CHANGELOG](https://github.com/ratatui/ratatui/blob/main/CHANGELOG.md)), but it clips silently, never adding `…`. Every `…` in the spec must come from application code.

## Crate survey

Adoption counts are crates.io reverse-dependency totals (2026-11-15, [crates.io API](https://crates.io/api/v1/crates/<name>/reverse_dependencies) `.meta.total`).

### Adopt

**`unicode-ellipsis` 0.6.0** ([crates.io](https://crates.io/crates/unicode-ellipsis) · [source](https://github.com/ClementTsang/unicode-ellipsis)) — "truncate Unicode strings to a certain width, automatically adding an ellipsis if the string is too long." `truncate_str(content, width) -> Cow<str>` (trailing `…`) and `truncate_str_leading` (leading `…`, useful for right-aligned columns). Updated 2026-07-06; authored/maintained by the bottom author (ClementTsang); deps: `unicode-segmentation ^1.13.3` + `unicode-width ^0.2.2` only; MSRV not declared on crates.io (leaf deps are edition-2021-era, far below our floor); 2 reverse deps (small but it is the reference implementation of exactly this job — bottom vendors its truncation through it: `src/utils/strings.rs`, `src/canvas/dialogs/process_kill_dialog.rs`, per GitHub code search 2026-11-15).

**`unicode-truncate` 3.0.0** ([crates.io](https://crates.io/crates/unicode-truncate) · [docs.rs](https://docs.rs/unicode-truncate/3.0.0/unicode_truncate/trait.UnicodeTruncateStr.html)) — "Unicode-aware algorithm to pad or truncate `str` in terms of displayed width." `unicode_truncate(max_width) -> (&str, usize)`, `unicode_truncate_start/_centered`, and `unicode_pad(target_width, align, truncate)` — the last replaces the spike's `pad_left`/`pad_right` with width-correct, exact-width output (a wide char that can't fit at the boundary is handled and the true width is returned). Updated 2026-08-20; MSRV 1.85; deps `itertools ^0.15` + `unicode-segmentation ^1` + `unicode-width ^0.2`; 53 reverse deps; gitui pins 2.0 (`Cargo.toml`, uses it in `src/strings.rs`, `src/popups/branchlist.rs`, …). Note 3.0 dropped the old `ignore_ansi` parameter — irrelevant here since our strings are scraped text, not ANSI, but pin awareness if that ever changes.

**`tui-input` 0.15.5** ([crates.io](https://crates.io/crates/tui-input) · [source](https://github.com/sayanarijit/tui-input)) — single-line input state: editing, cursor movement, backend event handling (`handle_event` over crossterm events), exposes cursor position for rendering. Updated 2026-09-26; **depends on `ratatui ^0.30.2`** (default `ratatui-crossterm` feature; also termion/serde optional) — i.e. current with our exact stack; MSRV not declared; 274 reverse deps (most-adopted crate in this survey). Covers §4's search mode (typing, `ctrl+u` clear is app-side, cursor rendering is ours but one `Span` split). History (`↑↓` last 10) is store state per spec, not an input-crate feature — nothing does that for us.

**`throbber-widgets-tui` 0.11.1** ([crates.io](https://crates.io/crates/throbber-widgets-tui) · [source](https://github.com/arkbig/throbber-widgets-tui)) — spinner/throbber widget with configurable frame sets and step state. Updated 2026-06-19 (same day as ratatui 0.30.2 — it tracks ratatui releases); **depends on `ratatui ^0.30`**; MSRV 1.88; default features = `std` only (`rand` is optional, keep it off); 78 reverse deps. Adopt with a custom frame list matching the TS app's `ink-spinner` "dots" frames (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`) for glyph parity; the widget also offers its own braille/full-cell styles.

**`tui-scrollview` 0.6.8** ([crates.io](https://crates.io/crates/tui-scrollview) · [source](https://github.com/ratatui/tui-widgets) `tui-scrollview/`) — `ScrollView`/`ScrollViewState`: render an arbitrarily tall child into a virtual area and scroll a viewport over it (by row or pixel-ish line offsets). Part of the ratatui-org `tui-widgets` suite (repo pushed 2026-11-11); MSRV 1.88; deps `ratatui-core ^0.1` + `ratatui-widgets ^0.3` + `indoc`; 46 reverse deps. This is the clean answer for §5.3's Queue panel — it is sections + bars + rows, not a uniform list, so `List` doesn't fit; the spike never implemented this scroll. Also the option for §5.5's "scrollable box when the terminal is shorter than the help overlay" (the simpler `…`-truncate fallback is also spec-legal).

### Evaluated, not adopted (with reasons)

**`tui-popup` 0.7.7** ([crates.io](https://crates.io/crates/tui-popup) · [source](https://github.com/ratatui/tui-widgets) `tui-popup/`) — renders a centered popup with border/title over the full frame; `PopupState` (position/dragging) is explicitly "experimental and the exact API will likely change" (README). Reading its source (`tui-popup/src/lib.rs`): **no backdrop dimming** — the spec's dimmed-browse-surface look still needs the buffer pass. The help/quit boxes are fixed, spec-pinned geometry (§5.5: "centred, 46-column box") with rounded borders and custom content, so `tui-popup` saves ~10 lines while giving up control. Keep the spike's `Clear` + `center_rect` + `Block` + `dim_except` (~15 lines). Revisit only if a third generic popup appears.

**`tuirealm` 4.1.0** ([crates.io](https://crates.io/crates/tuirealm) · [source](https://github.com/veeso/tui-realm)) — the one real *component framework* in this ecosystem (components, focus graph, own event loop/message queue). Actively maintained (4.1.0, 2026-05-02; MSRV 1.88; `ratatui ^0.30` core dep; extra always-on deps: `bitflags`, `dyn-clone`, `lazy-regex`, `thiserror` — 30 reverse deps). **Rejected:** spec §4 requires exactly one central input router dispatching on a focus enum, with components *forbidden* from registering their own handlers — tuirealm's architecture is the opposite trade (framework-owned event distribution), it would own the render loop shape, and the BROWSE screen has ~20 keys across 6 modes, well inside hand-rolled territory. The #15/#17 architecture decisions ("fresh internal architecture", "router maps 1:1") point the same way.

**`tui-widget-list` 0.15.4** ([crates.io](https://crates.io/crates/tui-widget-list)) — a stateless, scrollable list of arbitrary child widgets. Active (released 2026-11-15; deps `ratatui-core`/`ratatui-widgets`; 28 reverse deps). **Not needed:** our rows are `Line`s, which builtin `Table`/`List` render natively with better state integration (`highlight_style`, `scroll_padding`); this crate earns its keep when list entries are themselves stateful widgets.

**`tui-textarea` (rhysd) 0.7.0** — **stale and incompatible:** last release 2024-10-22, declares `ratatui ^0.29.0` ([crates.io deps](https://crates.io/api/v1/crates/tui-textarea/0.7.0/dependencies)), which semver-excludes ratatui 0.30's split crates. Use its successor instead ↓.

**`ratatui-textarea` 0.9.4** — the **ratatui-org fork** of rhysd's crate ("maintained independently", per its README, pointing at [ratatui discussion #2367](https://github.com/ratatui/ratatui/discussions/2367#discussioncomment-15664087)): updated 2026-10-31, MSRV 1.86, built on `ratatui-core ^0.1` + `ratatui-widgets ^0.3` (0.30-native), 160 reverse deps, and it is what gitui uses (`src/components/textinput.rs`). **Not adopted now** — the search line is single-line (`tui-input` is the lighter exact fit) and the spec has no multi-line editor. Record it as the known-good choice if that ever changes.

### Also noted

- `tui-scrollbar` (in the ratatui-org suite) exists for scrollbar rendering; ratatui's builtin `Scrollbar` widget already covers the optional need.
- The full `tui-widgets` umbrella 0.7.12 (crates.io, 2026-09-24) re-exports the suite behind features (`popup`, `scrollview`, `prompts`, `scrollbar`, `bar-graph`, `big-text`, `box-text`, `cards`, `equalizer`, `qrcode`); we can depend on the standalone crates we need instead — same MSRV (1.88), same repo.
- `tui-prompts` 0.6.8 (same suite): prompt widgets (text/confirm/select). Our quit prompt is a fixed spec-pinned box, not a generic prompt — skip.

## How prominent ratatui apps solve the same concerns

Surveyed from each repo's default branch on 2026-11-15 (Cargo.toml + targeted code search). Pattern across all four: **builtin widgets + `unicode-*` text crates + hand-rolled thin glue.** None uses a component framework.

| App | Stack (from its Cargo.toml) | Truncation/ellipsis | Lists/scroll | Progress | Overlays/footer |
|---|---|---|---|---|---|
| **gitui** (gitui-org/gitui, pushed 2026-10-06, ★22.7k) | `ratatui 0.30` (default-features off), `crossterm 0.29`, `unicode-truncate 2.0`, `unicode-segmentation`, `unicode-width 0.2`, `ratatui-textarea 0.8` | `unicode_truncate` in `src/strings.rs`, popups (`branchlist.rs`, `remotelist.rs`, …) | own `src/ui/scrollbar.rs` + `components/utils/scroll_vertical.rs` (predates builtin `Scrollbar`) | own components | hand-rolled popup components (`src/popups/*`); textarea wraps their `textinput.rs` |
| **bottom** (ClementTsang/bottom; crate `bottom` 0.15.0, upd 2026-11-01) | `ratatui 0.30.2` + `ratatui-core 0.1.2` + `ratatui-crossterm 0.1.2` (split crates), `crossterm 0.29`, `unicode-ellipsis 0.6.0`, `unicode-segmentation 1.13.3`, `unicode-width 0.2.2` | **`unicode_ellipsis`** in `src/utils/strings.rs` (+ dialogs) — the same crate recommended here | own canvases/tables | **builtin `Gauge`** (`src/canvas/widgets/mem_basic.rs`, `cpu_basic.rs`) | hand-rolled dialogs/help |
| **yazi** (sxyazi/yazi, pushed 2026-11-13) | `ratatui-core 0.1.2` + `ratatui-widgets 0.3.2` (split crates, no umbrella), `unicode-width 0.2.3`, `unicode-normalization`; workspace `rust-version 1.99` | own element system — `yazi-binding/src/elements/line.rs` implements its own ellipsis | own widget layer (`yazi-widgets`) | own | own (it is a full file-manager UI stack) |
| **atuin** (ellie/atuin) | `ratatui 0.30.0`, `crossterm 0.29` (`use-dev-tty`), `unicode-width 0.2` (crates/atuin/Cargo.toml) | width math with `unicode-width` | **hand-rolled `HistoryList`** with its own `ListState {offset, selected}` + `get_items_bounds` (`search/history_list.rs`) — the classic tui-rs pattern, chosen for custom column rendering | n/a | hand-rolled |

Take-aways: (1) nobody has a flexbox — fixed/boundary math lives in small layout functions, exactly like our `compute_layout()`; (2) width-correct text handling is universally delegated to `unicode-width`-family crates (bottom via `unicode-ellipsis`, gitui via `unicode-truncate`) rather than hand-rolled char math; (3) hand-rolling persists only where apps predate a builtin (gitui's scrollbar) or need bespoke per-row rendering (atuin's list) — both now covered for us by builtin `Table`/`List`/`Scrollbar`; (4) yazi is the counter-example that building a private widget kit is possible but is a product decision, not a default.

## MSRV, dependency weight, cross-compile

- **MSRV:** every adopted crate is ≤ 1.88 or undeclared (unicode-ellipsis, tui-input) — the project's effective floor is **ort's 1.92** (per the #17 research), so none of these constrain the toolchain. ratatui 0.30.2 = 1.88, tui-widgets suite = 1.88, unicode-truncate = 1.85, ratatui-textarea = 1.86, throbber = 1.88, tuirealm = 1.88 (rejected anyway).
- **Dependency weight:** net new crates are small: `unicode-ellipsis` and `unicode-truncate` share the leaf pair `unicode-segmentation` + `unicode-width` (the latter already in-tree via ratatui), plus `itertools` (already common); `tui-input` re-uses `ratatui`/`crossterm`; `throbber-widgets-tui` re-uses `ratatui` (default features = `std` only — no `rand`); `tui-scrollview` re-uses core+widgets plus `indoc`. Roughly five new leaf-level crates, zero new heavyweight trees.
- **Cross-compile (cargo-zigbuild linux-gnu, per #17):** all adopted crates are pure Rust — no C deps, no cc builds, no musl-only assumptions, no system libraries. Nothing here changes the #17 cross-build plan. (Contrast: this is why `textwrap`-with-smawk-style heavy deps were avoided too — and it isn't needed; builtin `Paragraph` wraps.)
- **Pinning:** pre-1.0 churn applies (ratatui 0.30.x restructure; expect a 0.31) — same mitigation as #17: pin exact versions.

## Risks / caveats / not verified

1. **Not compiled.** No candidate was built against ratatui 0.30.2 here. `tui-input ^0.30.2`, `throbber ^0.30`, and the tui-widgets suite declare 0.30-compatible reqs on crates.io, which is strong evidence but not a build. First workspace build (ticket #21) should `cargo update --dry-run`-check the five adoptions together.
2. **`unicode-ellipsis` MSRV is undeclared** on crates.io (version 0.6.0) — verified only that its two deps are `unicode-segmentation ^1.13.3` / `unicode-width ^0.2.2`. If a floor matters, it will resolve far below 1.92, but this is inference, not a published number.
3. **`unicode-truncate` 3.0 API changed** (no `ignore_ansi` param). Fine for scraped text; if ANSI-laden strings ever flow into list cells, re-check.
4. **Table vs List for the results panel is an implementation choice**, deliberately left open: `Table` fits the §3 column spec best; `List`-of-Lines is simpler if column widths end up hand-managed anyway. Both have `scroll_padding` + `highlight_*` — the scroll-window decision is independent of that choice.
5. **gitui's dim/overlay internals were not read line-by-line** (code search for `Modifier::DIM` returned nothing conclusive); the claim "apps hand-roll overlays/footers" rests on the repo structure (`src/popups/*`, custom `src/ui/scrollbar.rs`) and is safe at the level asserted.
6. **Spinner frame parity** with ink-spinner's "dots" set needs the literal frame list from `ink-spinner` at implementation time (visual parity item, per the behavioral-surface doc's glyph rules).
7. `tui-scrollview` for the Queue panel is a recommendation, not a spike-proven fit; the fallback is offset-slicing the line vector (~20 lines). Decide when implementing §5.3.
